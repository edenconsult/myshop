{% comment %} One key per dialog open, so a double click or a slow network that posts the same correction twice lands in the ledger as one adjustment. The POST response is the refreshed row, not a dialog, so close on arrival — but only on an arrival that actually saved. views.py answers EVERY business failure of adjust_batch (stale batch, bad reason, an inventory that no longer agrees with the ledger) by rendering the same row with an `error` key at HTTP 200, so event.detail.successful is true for those too and the row alone would hide the sentence behind this dialog. The close is therefore gated on the swap NOT landing [data-stock-error] in this product's row; when it did, the dialog stays open, keeping the reason and units typed, and copies the pill's sentence into [data-adjust-error]. A real 4xx/5xx (htmx 2.0.11 swaps nothing, but after-request still fires) leaves that element's own copy standing: the batch list may be stale. The binding is htmx's own: 2.0.11 compiles hx-on handlers with new Function("event", code), so the event is named event here (not the Alpine-only $event), and the value carries no raw double quote. {% endcomment %}
