## Problem

A new person — the owner's replacement at the counter, or a cashier on their first day — has nothing to learn from. `README.md` explains how to install the shop on a machine, and the tests explain what the code promises, but there is no document that shows what each screen looks like and which buttons to press. The app is entirely htmx-and-modals: most of it never appears in a URL bar, so "go to `/products/receipts/receive/`" is not an instruction a human can follow.

The system is also full of labels that overpromise ("Fast Barcode Lookup", "accept Cash, MoMo, or Card payments", "manage refunds", "Download CSV" that downloads nothing). An onboarding document that repeats those labels teaches the new person to stop trusting the screen.

## What this delivers

Thirteen numbered Markdown chapters in `docs/onboarding/`, each a task the system is allowed to perform, illustrated by screenshots captured from the running app, covering all 54 app routes from the login form to the printed receipt. Alongside them, real sample artifacts — the 80 mm receipt PDF, the A4 day-batch PDF, the A4 report PDF, both CSVs — downloaded from the app rather than described.

The document is generated by a committed harness, so when a screen changes, re-shooting is one command rather than an afternoon.

## Who reads it

Two people, one install, two journeys:

- **The owner (ADMIN).** Sees the hub, the catalogue, deliveries, counts, ledger, reports and accounts. Chapters 02–07 and 10–12 are their track.
- **The cashier (SALEPERSON).** `GET /` renders the till for them and the dashboard for the owner ([core/views.py:113-120](file:///C:/RebuildEden/django/myshop/core/views.py#L113)), so a cashier's entire screen world is chapter 08 and chapter 09. Everything else is refused at the URL level and lands on the login page.

Chapter 01 is shared. Chapter 13 is for whoever has to keep the shop running.

## Verified current state (facts this plan depends on)

- **`.env` outranks the environment.** `load_dotenv(BASE_DIR / ".env", override=True)` at `myshopproject/settings.py:13` re-applies the file's `POSTGRES_DB` and `CELERY_*` over any exported value, which is why isolation happens in a settings shim and not in a launcher variable (see "Scratch database and broker isolation").
- **54 app routes** in the working tree on 2026-11-04: 11 in `authapp/urls.py`, 43 in `core/urls.py` (1 `base`, 1 `help/`, 25 under `products/`, 16 under `orders/`), counted with the `products/` and `orders/` `include([...])` prefixes folded in. Committed `HEAD` has **53** — `/help/` is the other lane's uncommitted addition, along with four `receipts/` routes that took chapter 05's share from five to nine. `/admin/`, `/__reload__/`, static and media are infrastructure, not features. Because the count is a moving target while that lane lands, `verify.py` does not hard-code it: it reads the number stated here and fails if the URLconf and the matrix disagree (see the plan's Task 7).
- **The dev DB is applied through `core/0023`** (`showmigrations` confirmed 2026-11-03), so the whole delivery-draft workflow — `0021_stock_receipt_drafts`, `0022`, `0023_receipt_delivery_request_key` — is live and shootable.
- **Migrations through 0023 post-date the price-trail work.** `StockBatch.price_before` / `price_applied` exist and are written, but no template renders them: `core/templates/core/inventory/receipt_detail.html` is still an 8-column table. That is unimplemented Task 8 of `docs/superpowers/plans/2026-11-03-multi-line-receipt-pricing.md`. The tutorial documents it as absent.
- **Print means download.** Every "Print" control returns a `Content-Disposition: attachment` PDF from WeasyPrint. There is no `window.print`, no `@media print` for a browser, in any template.
- **The roll is 80 mm and hand-measured.** `receipt_sheet_length_mm` (`core/views.py:1326`) computes the sheet height because WeasyPrint refuses content-sized pages; `RECEIPT_COLOPHON_HEIGHT_MM = 27.0` (`core/views.py:1323`).
- **The receipt-button window is real.** `make_order` counts today's orders between 06:00 and 20:00 (`core/views.py:1189-1194`) and the settlement panel only shows "Download Receipt" when that count is truthy. `TIME_ZONE = "UTC"` (`myshopproject/settings.py:132`) and Ghana is UTC+0, so the window is the shop's trading day — a sale rung up after 20:00 leaves the cashier with no reprint entry point at all.
- **The register sends no idempotency key.** `pos_register.html` posts only the cart; `Order.checkout_request_key` exists and `checkout()` implements full replay detection, but with no key from the UI each tap mints a new one. A double-tap books twice. The tutorial must say so.
- **Stock is not typeable.** `Product.save()` refuses any stock change outside the inventory services, so every "how do I fix the count" answer goes through `receive_stock` or `adjust_batch`.
- **Dialogs are htmx fragments.** The Receive Delivery dialog (`core/templates/core/products/modals/receive_stock.html`) is opened by a button, and only `?view=add`, `?view=import` and `?view=out-of-stock` auto-open anything. A capture engine that cannot click will not see most of this system.
- **Draft autosave is 700 ms-debounced** (`receive_stock.html:181`), receipts paginate at 25 (`core/batch_views.py:311`), the POS grid at 12 and the ledger at 10 (`core/views.py:64`, `:66`).
- **No category or supplier screens exist.** Category is a five-value `TextChoices` enum; supplier is `CharField` free text on the receipt. There is nothing to photograph.
- **No email is ever sent** — no `EMAIL_*` key in settings, no password-reset route. A cashier who forgets their password needs the owner physically.

## Chapter anatomy

Every chapter uses the same five blocks, so a reader who learns the shape once does not relearn it per feature:

1. **What this is for** — two or three sentences in shop words, not system words.
2. **You need** — the role that can open it, the screen it lives on, how to get there from where the reader already is, and any data that must already exist.
3. **Steps** — one screenshot per step. The caption is what the reader should be able to see for themselves; anything not visible in the frame does not belong in the step.
4. **When it goes wrong** — the refusal, the error band, the silently missing button, each quoted verbatim from the template and explained in one line.
5. **Notes & limits** — what this screen will never do, what the label promises that the code does not keep, and what only the other role can see.

Currency is written as the screen writes it (`GH₵`), and where the success banner says `GHs` the quote is verbatim with a note, not silently corrected.

## The capture engine

### Scratch database and broker isolation

`POSTGRES_DB` is read at `myshopproject/settings.py:96`, but `settings.py:13` runs `load_dotenv(BASE_DIR / ".env", override=True)` and `.env` carries `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_HOST`, `POSTGRES_PORT`, `CELERY_BROKER_URL` and `CELERY_RESULT_BACKEND`. **An exported variable therefore loses to the file**, so "set `POSTGRES_DB` in the launcher" would silently keep pointing at the shop's own database. The same `.env` also puts a demo Celery worker on the live worker's broker and default queue, where the live worker would consume a demo import task and run it against the live database.

The launcher instead points Django at a settings shim that lives in this lane, `scripts/tutorial/demo_settings.py`, which star-imports the project settings and then overrides, after the `.env` load, the three things that must never be shared:

- `DATABASES["default"]["NAME"] = "myshop_tutorial"`
- `CELERY_BROKER_URL` / `CELERY_RESULT_BACKEND` on a separate Redis database index
- `CELERY_TASK_DEFAULT_QUEUE = "tutorial"`, with the demo worker started `-Q tutorial` so the shop's worker, listening on the default queue, cannot receive a demo task

`myshopproject/` is not modified. `run_demo_server.ps1` creates `myshop_tutorial` if absent, migrates it, and starts `runserver 127.0.0.1:8010 --settings=scripts.tutorial.demo_settings` plus that worker, because chapter 03 cannot be shot without a live worker consuming the import task.

Every harness entry point (`seed_demo.py`, `shoot.py`, `verify.py`) refuses to run unless `DJANGO_SETTINGS_MODULE` is the shim *and* `settings.DATABASES["default"]["NAME"]` is the scratch database — the guard reads the resolved settings rather than the environment, which is the only version that cannot be stomped. The script also refuses if the target database is `myshopproject`, and `shoot.py` refuses to capture if the page it loaded is not served from port `:8010`. The shop's own `:8000` and `:8001` processes and the running worker are never signalled.

Harness tests are a different matter: they run inside Django's own test database (`test_*`), never the scratch one, so `manage.py test scripts.tutorial` needs no shim and joins the project suite. The scratch database exists only to be photographed.

### State recipes

`seed_demo.py` writes through the real services — `checkout()`, `receive_stock()`, `adjust_batch()` — so FIFO allocations, frozen line costs and the batch/shelf invariant are genuinely produced rather than hand-planted. A tutorial whose numbers were typed in would teach the wrong thing, and the report chapter would show figures the app could not produce.

Each recipe is named, individually selectable, and re-runnable after a reset. The set the chapters need:

- **catalogue** — products spread across all five categories; some with an existing photo, some without (monogram fallback); in-stock, low-at-threshold, and depleted.
- **people** — the owner, two cashiers (one with their own sales today, one deactivated), with known passwords for the two cookie jars.
- **opening** — products created with initial stock, so `OPENING` receipts and their FIFO position are real.
- **delivery** — a booked two-supplier, multi-line purchase receipt; one line carrying a new selling price so the store-wide rule and its booked message are demonstrable; a cost change that makes a later row read `below cost`.
- **draft** — one unbooked `StockReceiptDraft`, for the "Delivery drafts" panel and Continue/Delete.
- **selling** — sales today across both cashiers and yesterday, for the KPI deltas, the by-cashier panels and "Your Takings" versus "Today's Takings"; one six-line sale for a tall receipt; one line sold below its batch cost, which is the only way to produce the rose negative-profit row honestly.
- **batches** — a partially sold batch and a depleted batch, for the batch-history columns.
- **out-of-balance** — one product forced off-balance with `QuerySet.update()`, which bypasses the save guard. This deliberately breaks an invariant the shop's books must never break, and is the single strongest reason the capture happens on a scratch database. It is what lets chapter 06 screenshot the lockout footer instead of describing it.
- **after-hours** — one sale with `created` pushed outside 06:00–20:00 by the same `QuerySet.update()` trick, so the missing "Download Receipt" button can be shown as a fact rather than a warning.
- **import** — a real CSV run through the worker, so the progress dialog, "Catalogue import complete" and the ledger refresh are captured as they happen.
- **removal** — throwaway SKUs to bulk-remove plus one protected product, so both halves of "removed N; M products were protected by stock or history" appear.

`MEDIA_ROOT` is shared with the live project, so recipes reuse existing product images read-only and never write a demo file into the shop's `media/`. A photo-less product is the more useful screenshot anyway.

### Shot harness

`shoot.py` drives Playwright (Python, sync API, Chromium) reading `shots.json`. Each manifest entry declares: id, chapter, required role, viewport (`desktop` 1440×900 or `phone` 390×844), the state recipe, and the interaction steps — navigate, click, fill, wait for the htmx swap, then capture. Two persistent contexts hold the ADMIN and SALEPERSON cookies, which is also what makes the role-refusal screenshots honest instead of staged.

Captures are `fullPage` where the point is the whole screen and clipped to one element where the point is a control, so a dialog can be shown both in context and legibly. Every shot is written to `img/<chapter>/` and appended to `SHOTLOG.md` with its route, role, viewport, recipe and timestamp — the record that lets a future reader tell which images went stale after a UI change.

For the paper itself: the three PDFs are downloaded into `samples/` as real artifacts. The 80 mm sheet additionally gets a PNG rendered from the same template and `static/css/receipt.css` dumped as standalone HTML and captured at paper width (80 mm ≈ 302 px at 96 dpi). The caption states that the PDF is the authoritative output and the PNG is a preview of the same markup, so nothing in the doc depends on headless Chromium's PDF viewer behaving.

### Verification gates

`scripts/tutorial/verify.py` runs at the close of every phase and fails loudly on:

- any app route absent from the route-to-chapter matrix, or any matrix row the URLconf does not have (54 routes listed as 59 entries, because `/`, `/products/` and `/orders/` each split by role or `?view=` mode). The expected count is read from the "Verified current state" bullet above rather than hard-coded, so a route landing in the other lane moves the spec and the gate in one edit;
- any image referenced by a chapter that does not exist, and any file under `img/` referenced by nothing;
- any path written in a chapter that is not resolvable against the scratch install through Django's test client using the method that chapter's step uses (a POST-only endpoint is checked by POST, so `make-order/` and the draft-save never fail the gate for the wrong reason); the point is that the typo'd `checks-orders` segment and the no-`{% url %}` reset-password route cannot silently rot in prose;
- any shot id in `shots.json` without a PNG, and any PNG under `img/` with no matching row in `SHOTLOG.md`.

The Django suite is unaffected (app code is untouched), but it is still run green before each phase commit, one suite at a time, because the other lane shares this tree.

## Ground rules for honest documentation

Carried over from the mockup porting rule that built this UI: every element is backed by real data or dropped.

- **No screen is photographed that does not exist.** The features with no UI — the price-before/price-applied trail, category and supplier master pages, an active/inactive product toggle, tender type and change due, refunds or voids of a booked order, self-service password reset, a browser print dialog, an import preview or column mapper, a low-stock notification — appear as stated absences in the relevant chapter's Notes & limits, never as a pending step.
- **A promise the code does not keep is named at the moment the reader meets it**, not collected only in chapter 13: "Void Cart" empties an unsent cart and voids nothing; the hub's "Download CSV" navigates instead of downloading; "Instant Receipts" hides its button outside 06:00–20:00; barcode scanners are not integrated; the receipt says "Served by" because it records a cashier, not because it records a refund.
- **The older screen stays older.** `/orders/check-orders/` and its `/days` POST are fully wired but linked from nowhere; they are documented once, in chapter 13, as reachable by typing the URL, with the year-blending bug in `retrieve_todays_sale` noted.
- **A correct refusal is shown as what it looks like.** `@user_passes_test` bounces an authenticated-but-unauthorised user to the login page, and `signin` discards `?next`, so "no, you can't see that" and "your session ended" are the same screenshot. The reader is told this in chapter 01 so a cashier does not think they broke something.
- **The htmx failure mode gets a frame.** An expired session inside a partial swaps the login card *into the table*, because nothing emits `HX-Redirect`. That is a real thing a new cashier will see.
- **Captions describe, steps instruct.** A caption says what is on screen; it does not claim causation the app has not demonstrated.
- Where the audit and the tree disagree, the tree wins, and the spec is corrected. Line numbers are re-verified per chapter because `core/views.py` moved 10 lines between two audits on the same day.

## Risks

- **Viewport truth.** Phone shots at 390 are honest; desktop layouts have only ever been judged by construction in this project. If a 1440 capture reveals a broken layout, that is a finding for the owner, not something to crop around.
- **Line numbers rot.** Two audits of `core/views.py` on the same day disagreed by ~10 lines. Citations are re-checked per chapter at writing time, and the matrix keys on URL patterns, which move far less.
- **Worker dependency.** Chapters 03 and 07 cannot be shot with Celery down, and a down worker looks identical to a hung import. Phase 2 proves the worker consumes from the scratch install before any prose is written.
- **Shared `MEDIA_ROOT`.** Recipes read existing images and never write demo files into the shop's media folder.
- **Binary weight.** ~100–115 PNGs, committed by owner decision. Mitigation if it later hurts: generated into an ignored folder and re-created by `shoot.py`, with the committed set trimmed to one image per step that a reader cannot do without.
- **Concurrent lane.** This work adds files only under `docs/onboarding/` and `scripts/tutorial/`, plus `scripts/__init__.py` and `pyproject.toml`/`uv.lock`. Staged by explicit path, never `git add -A`, and only one test suite runs at a time.

## Out of scope

Installing the shop, the Windows startup tasks, backups and the log locations (all already in `README.md`; chapters point at them instead of duplicating). Fixing any of the gaps chapter 13 lists — the price-trail column, the hub's mislabelled cards, the `checks-orders` typo, the after-hours button, the missing `HX-Redirect` — each of those is a separate feature decision with its own spec. The in-app Help idea (turning chapter 13 into the hub's currently-dead "Help & Support" card) is a feature, not a documentation task, and stays open.

## Re-shoot playbook

`run_demo_server.ps1` → `seed_demo.py --reset <recipes>` → `shoot.py --chapter <n|all>` → `verify.py`. The manifest is the source of truth for which screen looks like what; `SHOTLOG.md` timestamps say which images are older than the code that drew them. A feature change that moves a screen should re-shoot the affected chapter in the same commit as the change, and the chapter's own "you need" block is the first thing to edit when a route or a label moves.
